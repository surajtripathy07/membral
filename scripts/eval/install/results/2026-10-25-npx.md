# Install, rung three: `npx membral up` from packed tarballs

Date: 2026-10-25. Box 1.5 of `docs/goals/2026-10-25_beyond-claude-mem_goal.md` (Lever 1).
Subject: branch `l1-npx` (from main `4a191a92`). Compare with `2026-10-25-rung2.md` (a built checkout) and
`2026-10-25-baseline.md` (the Docker path).

**This run used two packed tarballs from the local build, not a published package.** `npm publish` is a human gate and
was never run. The npm registry was not involved in installing Membral itself; npx took both packages from local files.

## What changed

- The server ships as its **own package**, `@membral/server`, not inside the CLI. Reason: `apps/cloud` prebuild packs the
  CLI into `public/membral-cli.tgz`, which the hosted app serves; a 270 MB server inside it would break the hosted deploy
  and every hosted user's install. (Driver decision, reversible; flagged for the maintainer.)
- `scripts/local/build-server.mjs --pack [--out-dir DIR] [--pack-dest DIR]` writes `package.json` into the output
  (name `@membral/server`, the CLI's version, `engines.node` as the CLI) and runs `npm pack`, producing
  `membral-server-<version>-<platform>-<arch>.tgz`.
  - The traced `node_modules` (24 top-level packages) ride along as `bundleDependencies`; plain `npm pack` would drop them.
  - The traced copies are missing files their own install scripts need (`sharp/install/check.js`), so the first npx
    install failed with exit 1. `--pack` now removes `preinstall`/`install`/`postinstall`/`prepare` from bundled packages in
    the output copy (sharp, onnxruntime-node, onnxruntime-common). The packages are already built.
- `packages/cli/src/server-launch.ts` `findServerDir` order: `--server-dir`, `MEMBRAL_SERVER_DIR`, a checkout's standalone
  build (only when its `apps/cloud/server.js` exists), then the installed `@membral/server`, resolved from the CLI's own
  module URL and then from cwd. The missing-server error names all four options and the npx command.
- **The CLI's `package.json` does not depend on `@membral/server`.** That comes with publishing (human gate). Today the
  two packages are joined only by npx's `-p … -p …`, which installs both into one folder so the CLI can resolve the
  server.
- The CLI tarball is the one the hosted app serves, made by `packages/cli/scripts/pack.mjs` (unchanged).

platform.

The command (every `membral` call used the same two `-p` flags; paths shortened):

```

```

## Not covered

- **A published package.** Nothing was published and the registry path was not exercised: no dependency resolution of
  `@membral/server` by version, no `npx membral up` without `-p`, no `npm i -g`. Until the CLI depends on (or the docs
  name) `@membral/server`, the install line needs both `-p` flags.
- Other platforms: Linux and Intel macOS need their own `--pack` run. The wrong-platform refusal (`EBADPLATFORM`) was not
  tried.
- Extraction from sessions, `--foreground`, `membral logs`, the sweep job (launchd stubbed), a 10k-row store.
- A real Claude Code on the machine (hooks and MCP config written into `~/.claude`).
- The first search downloads the 145 MB embedding model and needs network, as in rung two.
- `up` prints the generated local password once, in clear (unchanged).
- Running `--pack` without `--out-dir` rewrites package.json scripts inside the build's own standalone folder; the
  checked runs used a separate output dir.

## Independent re-run

A second run from the same two tarballs, in a fresh scratch HOME with an empty `~/.claude` and an empty npm cache, Docker and `claude` absent from PATH, passed: `up` exit 0, `activeProfile` `local` (`source: local-stack`), health `store: "ready"`, setup wrote the SessionStart, SessionEnd and UserPromptSubmit hooks into `~/.claude/settings.json` (previous file kept as `settings.json.membral.bak`), `down` exit 0 and the port freed.

Setup's summary line "MCP Claude Code: configured" printed although no MCP entry was written: setup registers the server by running `claude mcp add-json … --scope user`, and when `claude` is not on PATH it prints the command to run instead but still counts the step as configured (`packages/cli/src/configure.ts`, not-found branch). That behaviour predates this change; on a machine with Claude Code installed the command runs. Filed as #583.

## Review fixes

An adversarial review of the first version found five problems, all fixed and re-run (both tarballs rebuilt, `up` exit 0 with the server dir printed, health `store: "ready"`, `down` exit 0, fresh scratch HOME and npm cache, Docker and `claude` absent, stdin closed). (1) The missing-server help no longer suggests `npx @membral/server`: the package is unpublished and its npm scope unclaimed, so anyone could register it; it now says to run `npm run build:local-server` in a checkout or pass `--server-dir` / `MEMBRAL_SERVER_DIR`. (2) The server and the checkout are found from the CLI's own module location only, never from cwd, so a global CLI started in an untrusted repo does not run that repo's server (or its migrations); `up` prints the chosen dir and whether it came from the flag, env, checkout or package. (3) `up` warns, naming both versions, when the server's version differs from the CLI's. (4) `--pack` without `--out-dir` now packs a temporary copy, so `apps/cloud/.next/standalone` is left as built; the tarball goes to `<repo>/dist` by default, which `.gitignore` covers (`dist/`). (5) On Linux the package pins `libc` (glibc or musl) next to `os`/`cpu`; not run on Linux. Test slip worth knowing: an unquoted `$X` holding the two `-p` flags is not word-split in zsh, which made npx fail with "Unknown command: up"; pass the flags literally. (Round 1 said npx fetched some other registry package named `membral`; a re-check found `membral`, `@membral/cli`, `@membral/server`, `membral-cli` and `membral-server` all 404 on the registry today, so that claim did not reproduce and is withdrawn.) The name and the scope are unclaimed; claiming them is a maintainer action before any publish or any public mention of `npx membral up`.
